# 工作流程与完成条件

## 变更记录

每项需求或缺陷记录：关联ID、触发场景、现状与目标、验收条件、非目标、影响模块/数据、验证方法。可使用GitHub Issue或PR，不要求为了小改动创建额外审批。

状态：待梳理 → 已定义 → 实现中 → 验证中 → 可合并 → 已合并。发布和部署分别记录；有按钮不算完成，已合并不算已上线。

## 执行

1. 读相关代码及文档、检查工作树；确认问题能复现。普通修复用小提交，分支可命名fix/主题或feat/主题，不强制重建用户现有分支。
2. 明确行为、验收和回归风险；复杂数据/架构取舍写ADR，简单样式修复无需ADR。
3. 实现最小闭环，保留人工决策和原文件只读约束。必要测试覆盖失败、取消、重启和边界，不堆实现镜像测试。
4. 按TESTING执行，记录环境、命令、结果、未覆盖范围。真实媒体不进仓库。
5. 自审差异、隐私、错误信息、资源分发、迁移及文档。使用PR模板；单人直提也遵循同样证据要求，不强制形式化PR。
6. 只有验收通过或缺口明确被记录，才标记实现完成。阻塞说明具体条件；不得静默降低验收。

## 完成定义

- 用户可走通入口、操作、结果、错误/空状态和返回；数据不会因后台更新丢失。
- 相关测试及交付检查通过；不能验证的实机/长期场景有明确记录。
- 功能、需求和使用说明一致；后续需求不冒充当前能力。
- 提交范围干净，无私人运行数据；提交号、发布版本和运行状态分别可核对。

## 变更级别

|类型|最低证据|
|---|---|
|文档|链接、命令及现状核对|
|低风险界面|语法、相关视觉/交互验证；无须为颜色写单元测试|
|识别/筛选/关系|固定合成样本、人工覆盖保护、边界回归|
|任务/数据/恢复|失败/取消/重启/旧数据与恢复证据|
|发布/依赖|源码归档、解压验证、许可证/隐私与安装范围|

紧急修复可缩小范围，但必须记录原因和欠缺验证；不能绕过源文件保护或隐私边界。发布不默认重启用户服务，已获授权的运行维护按安全停止、备份和状态恢复执行。
