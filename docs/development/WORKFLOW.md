# 开发与交付流程

适用于人工和 AI 贡献。以用户目标、变更风险和实际证据决定工作量。普通修复可在一个变更中走完全程，涉及数据迁移、任务恢复或物理整理的变更须独立验证失败与回滚路径。保持现有工作树与运行目录隔离。

|阶段|进入条件与工作|退出产物及责任|
|---|---|---|
|需求定义|复现问题或核对基线，明确用户场景、范围、优先级、验收条件、依赖和延后项|维护者在版本需求中确定范围。实现者记录需求 ID 或已有审计 ID，台账记录状态。|
|方案设计|核对现有模块、接口、数据和依赖。高风险取舍评估兼容性、失败恢复、隐私和权限|实现者给出可审查的方案。重要取舍记入 ADR，涉及数据或接口时同步对应契约。|
|实现与自审|用独立数据和合成媒体完成最小可用闭环，检查正常入口、旧数据和错误分支|变更关联需求 ID，更新受影响文档。状态进到待验收，写清实现与验证缺口。|
|验收与审查|按风险选择测试。界面验证浏览器行为，性能用同机基线，存储操作覆盖中断及重跑|审查人核对差异和证据。单维护者项目可自审并记录。只有通过逐项验收才记为通过。|
|发布准备|冻结候选提交，核对版本范围、未通过项、已知问题及升级回滚。解压源码包独立验证|发布者记录提交、包校验和、版本说明和实际验证范围。P0 缺口需先修复或由需求负责人明确调整范围。|
|发布与运行|核对发布授权；部署单独核对运行授权、服务状态、数据备份和回退路径|分别记录合并提交、Release 版本、部署版本和健康验证。失败时按运行手册处理，记录现场与恢复结果。|

角色是责任划分，可以由同一维护者承担。涉及发布、部署与原文件执行时沿用已有授权。发现验收不足时回到相应阶段，保留失败结果。范围调整记下旧目标、新目标、原因及相关验收变化，避免通过改状态或删场景放行。

## 风险与最低证据

|变更|最低证据|
|---|---|
|文档 / 需求|核对实际行为、版本和相对链接；需求、台账和路线图一致。|
|界面 / 交互|语法、相关桌面和窄屏场景、返回与错误状态；涉及图片时验证隐私。|
|识别 / 查询 / 性能|合成固定样本、人工覆盖及语义一致性；性能记录环境、统计口径和改前改后。|
|任务 / 数据 / 权限 / 文件操作|旧库与重复迁移、失败/取消/恢复、并发与权限边界、备份和回退。|
|发布 / 依赖|全量回归、提交与包对应、解压验证、第三方许可、隐私和发行说明。|

验证命令与报告口径见 [测试规范](TESTING.md)。使用 [变更审查模板](../../.github/pull_request_template.md) 保存证据，按 [发布流程](../RELEASING.md) 发布。当前 CI 为示例，实际检查由执行者记录。
