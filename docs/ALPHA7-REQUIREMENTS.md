# alpha.7 需求与验收

规划日期 2026-11-05。基线为已发布并在本机运行的 v0.1.0-alpha.6。本文定义下一迭代范围，全部条目当前均为待开发或待测量。

alpha.7 的目标是让大片库打开更快，在后台工作时仍能流畅选片，把刮削、质量审阅和整理恢复做成可日常使用的流程，并统一浏览、详情和管理区的导航。

## Epic、Feature 与 Story

P0 为发布必达。P1 在对应 P0 达标后实施，可单独延期。涉及物理文件操作的验收使用独立测试数据和合成媒体。

|E1 性能 / 首屏与索引|A7-01|P0|启动后尽快看到片库，刷新时不用重复等待|保留索引的日常冷启动以 1 秒为发布目标；首次建索引也争取 1 秒。预计无法立即展示结果时，在 1 秒内显示真实构建阶段和进度。搜索、排序和合集计数与基线一致。|
|E1 性能 / 查询和刷新|A7-02|P0|搜索、换筛选、翻页和打开常用管理列表时，结果能及时出现|主片库、媒体库文件、刮削任务、硬盘文件列表逐页取数；先审计已分页的入口，再修复随全库规模增长的请求或聚合。人工修改、扫描增量、整理绑定和恢复后，结果、计数与选中范围一致；旧响应不能覆盖新条件。标签在筛选区铺开展示，支持搜索、多选和全部或任意匹配。翻页和刷新保留已选项。|

## 跨功能约束

现有片库资料、人工决策、隐私、权限和恢复保护适用于全部 Story。以 Windows 本机为主验收环境。NAS 保持既有部署边界，兼容性和设备覆盖按实测记录。项目工作流与发布门槛见 [开发与交付流程](development/WORKFLOW.md)，具体依赖和验收证据进入 [交付台账](DELIVERY-STATUS.md)。

性能需求变更记录：2026-11-05 用户提出冷首屏 1 秒目标及进度条。保留索引重启目标由 1.5 秒调整为 1 秒，首次构建争取 1 秒，延用 3.5 秒发布上限并增加真实进度验收。

## 性能预算与测量口径

沿用 [alpha.6 性能报告](ALPHA6-PERFORMANCE.md) 的 Windows NTFS 参考环境，使用同一份 1 万/5 万条合成片库（含版本、分段、合集和质量记录），对已发布 alpha.6 与 alpha.7 候选同机对测。以下是拟定目标，具体基线由第一批测量补齐。

|5 万条场景|alpha.6 已有参考证据|alpha.7 P0 目标|
|---|---|---|
|空派生索引，冷首屏|约 4.55–4.59 秒，48 张卡片，简单 SVG|争取中位数 ≤ 1 秒。若未达到，发布上限仍为中位数 ≤ 3.5 秒，且每次等待均须符合下方进度条验收。分别报告索引构建和浏览器绘制时间。|
|保留索引重启 / 暖首屏|暖首屏约 164–242 ms；保留索引重启需同机补测|保留索引时，从启动服务到首屏可操作的中位数 ≤ 1 秒。暖首屏 ≤ 500 ms。|
|翻页及新筛选到正确结果可见|翻页 p95 286 ms；新搜索曾观测 472 ms，非 p95|翻页 p95 ≤ 300 ms；更换筛选或排序 p95 ≤ 700 ms。每场景至少 20 次，新条件与重复查询分开记录。|
|卡片点击到反馈和详情可操作|本机 alpha.6 抽样 4 个作品，详情 HTTP 约 77–82 ms|浏览器点击到反馈 p95 ≤ 50 ms，常规作品到详情与播放按钮可操作 p95 ≤ 200 ms。至少 20 次，区分首次与重复打开。独立记录剧照完成时间，覆盖快速连点及离开页面。|
|后台负载下浏览与播放|需补测|翻页 p95 ≤ 600 ms；本地可直放合成样片点击到首帧 p95 ≤ 2 秒。单独报告各负载及样本数。|
|响应、图片和内存|主片库列表 JSON 最大约 26 KB，服务进程峰值约 83 MB；真实图片解码需补测|主片库默认页 JSON ≤ 64 KiB，常用管理列表响应随页大小增长；首次加载记录可见卡片和相邻行请求数，滚动与反复进出详情后，服务峰值内存同负载较基线增长 ≤ 15%，浏览器内存及未完成请求数无持续爬升。|

测量记录硬件、浏览器、数据库及图片缓存状态、后台负载、数据形状、样本数。首屏从导航到可见卡片与主操作可用；首次缩略图绘制另报；同时记录进程启动耗时，避免把索引成本转移到启动后误判为加速。复用现有 benchmark/preview 脚本，并为缺失场景补测。每个数值对应独立环境证据，不外推至 NAS、exFAT 或所有图片大小。

冷启动各跑至少 3 次，每次启动新服务进程并打开新页面，记录中位数和最慢值。保留索引组使用已构建的持久索引，首次构建组从空派生索引开始。首屏验收以正确的卡片和可用主操作为准。

进度条验收：冷首屏等待达到 1 秒时，页面须已显示当前阶段，例如“检查片库索引”“正在建立索引”或“加载首页”。可取得总量时按已处理条数显示进度，阶段总量未知时显示不定进度。刷新或另开页面应读取同一个构建任务的状态；构建完成后自动显示片库，失败时显示原因和可重试入口。用人工延迟和失败注入覆盖长时间等待、完成、刷新及重试。进度出现的时间单独记录。

## 实施与发布顺序

P0 定义发布门槛，下表定义实际开发顺序。组内先解决依赖与风险，再做样式细节。

|批次|优先需求|完成后进入下一批的条件|
|---|---|---|
|1 首屏可用|A7-01、A7-02 的首屏查询部分|分开记录保留索引启动、首次构建和暖请求。验证 1 秒目标、进度与失败重试，确认筛选和合集结果一致。|
|2 日常选片|A7-02 余项、A7-11–13、A7-03、A7-14|先统一导航和列表，再调整卡片、详情和剧照。验证返回、跨页选择、隐私和草稿保护。|
|3 后台与文件安全|A7-04、A7-05|用第二批浏览链路测并发。文件恢复方案从第一批起核对身份、检查点和对账，实现在独立 NTFS 合成环境验收。|
|4 刮削与质量闭环|A7-06–07|验证失败分类与批量重试、人工锁定、证据审阅和版本对比。|
|5 候选验收|A7-16|所有 P0 按 ID 核对证据、升级回滚、全量回归及解压验证。|

P1 排序为 A7-15 浏览增强、A7-08 标签治理、A7-09 人物治理。A7-10 取决于设备可用性，具备条件即可单独验证。各批次交付证据记录在台账。

后续专题保留完整 NAS/多平台认证、转码与播放轨道、动态片单、通用视觉识别、自动发现外部高清源、跨卷搬迁及安装分发。日常扫描、质量和刮削使用只读原媒体；整理写入沿用对具体固定计划的人工批准。自动发现只提供审阅证据，文件替换和删除继续由用户决定。
